# Ticket & PR Tracker — Product Requirements Document

## 1. Document Purpose

This Product Requirements Document (PRD) defines the product scope, user experience, functional requirements, data model, system behaviour, analytics, exports, Chrome extension, security expectations, and acceptance criteria for Ticket & PR Tracker.

It is the primary product reference for design and implementation. Visual styling and detailed UI tokens will be defined separately in `design.md`. This document does not replace a technical architecture document.

## 2. Product Summary

Ticket & PR Tracker is a lightweight web application for recording work represented by Jira tickets and associating that work with GitHub pull-request (PR) links.

Users create a tracker by submitting a Jira ticket URL and manually choosing its category:

- **Development**
- **Support**

The application does not sign in to Jira, fetch Jira ticket contents, or attempt to read private Jira pages. The submitted URL is the source of truth. The application extracts the ticket identifier from the URL and uses that identifier as the tracker title. The full URL is retained and shown as the ticket reference.

When work is complete, the user selects an existing tracker and submits one or more GitHub PR URLs. The tracker is then marked completed according to the application's completion workflow. GitHub OAuth and PR-content inspection are not required for the MVP.

A Chrome extension provides a quick way to create a tracker from the current Jira page. The extension authenticates with the Ticket & PR Tracker application and sends the Jira URL to the application's backend. It does not connect directly to Jira or GitHub.

The application provides a dashboard, tracker search and management, calendar/list views, monthly and custom-range analytics, Excel export, and PDF reporting.

## 3. Product Goals

### 3.1 Primary goals

1. Make it quick to record a Jira ticket without manually copying ticket details.
2. Keep the Jira ticket URL as the authoritative reference.
3. Require an explicit user-selected category of Development or Support.
4. Associate one or more GitHub PR URLs with a tracker.
5. Provide a reliable record of when a tracker was started and completed.
6. Show useful monthly work statistics and trends.
7. Allow users to export their tracker and analytics data to Excel and PDF.
8. Reduce friction when creating trackers through a Chrome extension.

### 3.2 Success criteria

The product is successful when a user can:

- Sign in with Google.
- Create a tracker by submitting a valid Jira URL and selecting Development or Support.
- See the extracted ticket ID as the tracker title.
- Find trackers by ticket ID or CR/PR reference.
- Close a tracker by selecting it and submitting its GitHub PR URL(s).
- See accurate ticket, category, PR, and cycle-time metrics.
- Filter analytics by a preset or custom date range.
- Download an Excel workbook and a PDF report for the selected period.
- Create a tracker from the Chrome extension while signed in to the application.

## 4. Non-Goals

The following are explicitly outside the MVP scope:

- Jira OAuth, Jira API integration, or Jira account connection.
- Fetching Jira ticket titles, descriptions, comments, labels, status, assignee, or other ticket metadata.
- Reading private Jira pages or using Jira session cookies.
- AI classification, AI-generated descriptions, AI summaries, or AI-based categorization.
- Microsoft AI or Cloudflare Workers AI usage.
- GitHub OAuth or GitHub account connection.
- Fetching PR descriptions, source code, review information, checks, or merge status.
- Verifying that a submitted private PR exists or is merged.
- Automatically discovering PRs associated with a Jira ticket.
- Team-wide or organization-wide reporting in the initial release.
- Closing trackers from the Chrome extension in the MVP.
- Replacing Jira or GitHub as the systems where engineering work is performed.

## 5. Users and Permissions

### 5.1 Primary user

An individual developer or team member who needs a simple personal record of Jira work and associated PR references.

### 5.2 MVP roles

The MVP has one application role:

**User**
- Create trackers.
- View and search their own trackers.
- Edit permitted tracker fields.
- Close their own open trackers.
- Add PR references according to the tracker lifecycle rules.
- View their own analytics.
- Export their own data.

There is no administrator, manager, or team role in the MVP.

### 5.3 Data ownership

Every tracker, PR reference, analytics query, and export must be scoped to the authenticated user. A user must never be able to access another user's records by changing an ID or request parameter.

|---|---|

## 8. Information Model and Source of Truth

### 8.1 Jira ticket information

The application must not attempt to read the Jira page or retrieve ticket metadata.

The user supplies:
- Jira ticket URL.
- Category: Development or Support.

The application derives:
- Ticket ID from the URL, when the URL matches a supported Jira issue URL pattern.

The application stores:
- Original submitted URL.
- Normalized URL, where safe and useful.
- Parsed ticket ID.
- User-selected category.
- Application start date and status.

The application must not invent or display a Jira title or description. The visible tracker title is the parsed ticket ID. The visible ticket reference/body is the Jira URL.

Example:

Submitted URL:
`https://company.atlassian.net/browse/DEV-123`

Displayed tracker:
- Title: `DEV-123`
- Ticket link: `https://company.atlassian.net/browse/DEV-123`
- Category: `Development`

If the ticket ID cannot be parsed confidently, the application must ask the user to correct the URL or enter the ticket ID manually. It must not create a misleading ID.

### 8.2 Category

The category is mandatory and selected by the user. The allowed values are:

- `DEVELOPMENT`
- `SUPPORT`

The category must be visible in create forms, tracker lists, tracker details, filters, analytics, and exports.

No automatic classification is performed.

### 8.3 PR information

The user submits the GitHub PR URL. The application stores the URL as supplied after validation and safe normalization.

The application may parse a repository identifier and PR number from a conventional GitHub URL, but this is convenience metadata only. It must not call GitHub to verify the PR or infer its state.

The submitted PR URL is the source of truth for the PR reference.

## 9. Main User Journeys

### 9.1 Sign in

1. User visits the application.
2. User selects **Continue with Google**.
3. Better Auth performs the Google authentication flow.
4. The application establishes a secure session.
5. User is redirected to the dashboard.
6. The user can access only their own data.

### 9.2 Create a tracker in the web application

1. User opens Dashboard or Trackers.
2. User selects **Create Tracker**.
3. Application opens a dialog or dedicated form.
4. User pastes the Jira ticket URL.
5. User selects `Development` or `Support`.
6. Application validates the URL and extracts the ticket ID.
7. Application shows a review/confirmation state with the parsed ticket ID and category.
8. User submits the form.
9. Backend creates the tracker with `OPEN` status and a start timestamp.
10. Application displays success and the new tracker appears in the list/calendar/dashboard.

Required inputs:
- Jira ticket URL.
- Category.

Start date behaviour:
- Default to the current date/time at tracker creation.
- If the product design allows editing the start date, the user may select a different date before or after creation according to the permissions defined below.
- Store timestamps consistently in UTC and display them in the user's local timezone.

### 9.3 Create a tracker from the Chrome extension

1. User opens a Jira ticket in Chrome.
2. User clicks the Ticket & PR Tracker extension icon.
3. Extension checks whether the user has an authenticated application session.
4. If not authenticated, the extension provides a sign-in action that opens the main application.
5. Once authenticated, extension reads the active tab URL only after the user opens the extension UI.
6. Extension pre-fills the Jira URL field with the current tab URL.
7. User confirms or edits the URL.
8. User selects Development or Support.
9. User clicks **Create Tracker**.
10. Extension sends the URL and category to the application backend using the application's authenticated flow.
11. Backend validates and creates the tracker.
12. Extension displays success or an actionable error and provides a link to open the tracker in the main application.

The extension must not scrape the Jira page, inspect page content, read Jira cookies, or connect to Jira APIs.

### 9.4 Close a tracker and add PR references

1. User selects **Close Tracker** or an equivalent action.
2. Application displays the user's open trackers.
3. User searches for or selects the tracker to complete.
4. Application displays the selected ticket ID and Jira URL for confirmation.
5. User submits one or more GitHub PR URLs.
6. Backend validates URL format and checks for duplicates within the applicable scope.
7. Application saves the PR references.
8. User confirms completion.
9. Backend marks the tracker `COMPLETED` and records `completed_at`.
10. Dashboard and analytics are updated.

A tracker must not be closed merely because a PR URL was pasted into an unfinished form. Completion occurs only after the user confirms the close action.

### 9.5 View and search trackers

1. User opens the Trackers page.
2. Application displays a paginated list of the user's trackers.
3. User searches by ticket ID or PR/CR reference.
4. User may filter by category, status, or date range.
5. Selecting a result opens the tracker details view.

Search results must remain concise. They should show ticket ID, category, associated CR/PR reference(s), and status. Do not show Jira-derived title or description fields.

## 10. Functional Requirements

### 10.1 Authentication

**FR-AUTH-01 — Google sign-in**
The application must support Google sign-in through Better Auth.

**FR-AUTH-02 — Session**
The application must maintain a secure authenticated session across supported web application routes.

**FR-AUTH-03 — Sign-out**
Users must be able to sign out.

**FR-AUTH-04 — Protected routes**
Dashboard, tracker, analytics, and export functionality must require authentication.

**FR-AUTH-05 — Ownership enforcement**
All reads and writes must be scoped to the authenticated user on the backend, not merely hidden in the frontend.

### 10.2 Tracker creation

**FR-TRK-01 — Create action**
The application must provide a clear Create Tracker action.

**FR-TRK-02 — Jira URL input**
The create form must accept a Jira issue URL.

**FR-TRK-03 — URL validation**
The backend must validate the URL protocol and supported Jira issue URL format. It must reject malformed URLs and unsafe schemes.

**FR-TRK-04 — Ticket ID extraction**
The application must parse the issue key from supported URL patterns, including common Jira Cloud paths such as `/browse/PROJECT-123`.

**FR-TRK-05 — Manual correction**
If parsing fails or is ambiguous, the user must be able to correct the URL or provide the ticket ID manually. Any manually entered ID must be stored distinctly from an automatically parsed ID if this distinction is retained in the data model.

**FR-TRK-06 — Category selection**
The user must select exactly one category: Development or Support.

**FR-TRK-07 — Start date**
The tracker must receive a start timestamp at creation. If editing is supported, the interface must make the selected date clear.

**FR-TRK-08 — Initial status**
New trackers must have `OPEN` status.

**FR-TRK-09 — Duplicate prevention**
The application should prevent accidental duplicate trackers for the same user and Jira ticket ID. If duplicates are intentionally allowed, the user must receive a clear warning and explicitly confirm.

**FR-TRK-10 — No Jira content retrieval**
The application must not fetch Jira page contents, Jira metadata, or Jira APIs.

### 10.3 Tracker viewing and editing

**FR-TRK-11 — Tracker list**
Users must be able to view their trackers in a list/table.

**FR-TRK-12 — Tracker detail**
A tracker detail view must show:
- Ticket ID.
- Jira URL as a clickable external reference.
- Category.
- Start date.
- Status.
- Associated PR URL(s).
- Completion date, if completed.
- Cycle time, if completed.

**FR-TRK-13 — Category is fixed after creation**
The category is selected once, at tracker creation, and is then displayed as a label. It cannot be switched afterwards.

**FR-TRK-14 — Edit start date**
If enabled, users may correct the start date. Changes must recalculate cycle time and be reflected in reports.

**FR-TRK-15 — No Jira title/description**
No Jira title or description fields should be requested, fetched, generated, or displayed.

### 10.4 PR reference management

**FR-PR-01 — Add PR URL**
Users must be able to submit a GitHub PR URL when closing a tracker.

**FR-PR-02 — Multiple PRs**
A tracker may have multiple PR URLs.

**FR-PR-03 — URL validation**
The application must validate that submitted values are valid HTTPS GitHub pull-request URL formats. The MVP may support `github.com/{owner}/{repo}/pull/{number}`.

**FR-PR-04 — No GitHub API dependency**
The application must not require GitHub OAuth or call GitHub APIs in the MVP.

**FR-PR-05 — PR count**
PR count must be based on unique stored PR records, not on inferred GitHub state.

**FR-PR-06 — Duplicate prevention**
The same normalized PR URL must not be counted twice for the same tracker. The product should also warn if the same PR is already associated with another tracker belonging to the same user.

**FR-PR-07 — PR display**
Show the submitted PR URL as a clickable external link. If repository and PR number were parsed from the URL, they may be shown as compact reference metadata.

**FR-PR-08 — No PR content**
Do not fetch PR title, body, author, labels, reviews, checks, merge state, or code.

### 10.5 Tracker completion

**FR-CLOSE-01 — Select open tracker**
The close workflow must allow selection only from the user's open trackers.

**FR-CLOSE-02 — Add PR references**
The close workflow must accept one or more PR URLs.

**FR-CLOSE-03 — Completion confirmation**
The user must explicitly confirm completion.

**FR-CLOSE-04 — Completion timestamp**
The backend must record `completed_at` when the tracker is successfully completed.

**FR-CLOSE-05 — Completed state**
The tracker status must change to `COMPLETED`.

**FR-CLOSE-06 — Completion integrity**
The completion operation must be idempotent or otherwise protected against duplicate submissions.

**FR-CLOSE-07 — Reopening**
Reopening a completed tracker is not required for the MVP. If later supported, it must be an explicit action and must define how prior completion timestamps and analytics are handled.

**FR-CLOSE-08 — Post-completion PRs**
The MVP should define whether additional PRs can be attached after completion. Recommended default: allow adding a reference to a completed tracker without changing its completion date, while recording the PR's own added timestamp. This behaviour must be consistent in the UI and exports.

### 10.6 Search and filtering

**FR-SEARCH-01 — Ticket ID search**
Users must be able to search by ticket ID.

**FR-SEARCH-02 — PR/CR search**
Users must be able to search by PR number, repository reference, or full PR URL where available.

**FR-SEARCH-03 — Category filter**
Users must be able to filter Development and Support trackers.

**FR-SEARCH-04 — Status filter**
Users must be able to filter Open and Completed trackers.

**FR-SEARCH-05 — Date filter**
Users must be able to filter by start date and completion date.

**FR-SEARCH-06 — Minimal result fields**
Search results must show ticket ID, category, CR/PR reference(s), and status. The Jira URL may be accessible through the ticket ID or a link affordance. No title or description is required.

## 11. Date and Analytics Rules

Correct date semantics are essential. Each metric must use a defined timestamp.

### 11.1 Start date

- Default start date is the tracker creation timestamp.
- It is not inferred from Jira.
- If the user can edit it, preserve the fact that the date was manually changed if auditability is required.
- Display in the user's local timezone.

### 11.2 Completion date

- Completion date is the timestamp at which the user confirms completion in the application.
- It is not the GitHub merge date.
- It is not the date on which the Jira ticket was created or updated.

### 11.3 PR added date

- Each PR reference has its own `created_at` timestamp representing when the URL was added to the tracker.
- PR activity charts use this timestamp.

### 11.4 Cycle time

`Cycle time = completed_at - start_date`

- Only completed trackers have a final cycle time.
- Open trackers must not be included in average completed cycle time.
- Store or calculate durations consistently, preferably in seconds or minutes, and format for display as days/hours.
- If a start date is after the completion date, prevent the invalid update or flag the record for correction.

### 11.5 Monthly grouping

Metrics must not use one generic date field for all charts.

| Metric | Date used |
|---|---|
| Trackers started | `start_date` |
| Trackers completed | `completed_at` |
| PR references added | PR `created_at` |
| Average cycle time | `completed_at`, using trackers completed in the month |
| Open tracker age | Current time minus `start_date` |

For a custom range, include records whose relevant metric timestamp falls within the selected range. The UI and exports must use the same definitions.

### 11.6 Open trackers in a period

For a selected period, the “Open trackers” card should be explicitly defined as either:
- Trackers currently open at the time of viewing; or
- Trackers that were open at the end of the selected period.

Recommended MVP behaviour: show **Currently open** as a current-state metric and label it accordingly. Do not present it as a historical end-of-period count unless historical status snapshots are implemented.

## 13. Data Model

The following is a logical product data model. Exact SQL types and Better Auth table details are implementation decisions.

### 13.1 User

Better Auth owns the authentication-related records. Application records reference the authenticated user ID.

### 13.2 Tracker

| Field | Suggested type | Required | Description |
|---|---|---:|---|
| `id` | TEXT/UUID | Yes | Unique tracker identifier |
| `user_id` | TEXT | Yes | Owner |
| `ticket_id` | TEXT | Yes | Parsed or user-corrected issue key |
| `jira_url` | TEXT | Yes | Original/normalized Jira issue URL |
| `category` | TEXT/ENUM | Yes | `DEVELOPMENT` or `SUPPORT` |
| `start_date` | INTEGER/TIMESTAMP | Yes | Work start timestamp |
| `start_date_source` | TEXT | Yes | `CREATED` or `MANUAL`, if tracking provenance |
| `status` | TEXT/ENUM | Yes | `OPEN` or `COMPLETED` |
| `completed_at` | INTEGER/TIMESTAMP | No | Completion timestamp |
| `created_at` | INTEGER/TIMESTAMP | Yes | Record creation timestamp |
| `updated_at` | INTEGER/TIMESTAMP | Yes | Last update timestamp |

Recommended constraints:
- Primary key on `id`.
- Foreign key to user.
- Category check constraint.
- Status check constraint.
- Index on `(user_id, start_date)`.
- Index on `(user_id, completed_at)`.
- Index on `(user_id, status)`.
- Index on `(user_id, category)`.
- Unique `(user_id, ticket_id)` if duplicate trackers are not allowed.

### 13.3 PullRequestReference

Recommended constraints:

### 13.4 Optional audit events

## 15. URL Validation and Normalization

### 15.1 Jira URLs

- Accept HTTPS URLs only.
- Support the configured Jira host or an explicitly allowed set of Jira hosts.
- Parse the issue key from supported URL paths.
- Reject `javascript:`, `data:`, `file:`, and other non-HTTPS schemes.
- Do not fetch the URL from the backend.
- Do not follow redirects or perform network requests to validate a Jira URL.
- Store the submitted URL and a normalized representation if needed.
- If multiple Jira domains are used, provide a controlled configuration rather than accepting arbitrary domains without validation.

### 15.2 GitHub PR URLs

- Accept HTTPS GitHub pull-request URL formats.
- Expected common pattern: `https://github.com/{owner}/{repo}/pull/{number}`.
- Do not fetch the URL.
- Do not verify repository visibility or PR state.
- Parse owner, repository, and PR number only from a valid supported URL.
- Normalize trailing slashes and harmless URL variations for duplicate detection.
- Preserve a safe clickable URL for display.

## 16. Security and Privacy Requirements

1. Use Better Auth for application authentication.
2. Require authentication for all private application data and APIs.
3. Enforce user ownership in backend database queries.
4. Never read or store Jira or GitHub session cookies.
5. Never ask users to paste passwords or access tokens.
6. The Chrome extension must not access Jira/GitHub cookies or page DOM.
7. Restrict extension permissions to the minimum required.
8. Use HTTPS for application communication.
9. Validate and normalize all submitted URLs.
10. Do not fetch arbitrary user-supplied URLs from the backend; this avoids unnecessary SSRF exposure.
11. Protect create, completion, and export endpoints with appropriate rate limits.
12. Avoid exposing private tracker data in logs.
13. Do not include secrets in frontend bundles or extension packages.
14. Ensure exports are generated only for the authenticated user.
15. Define data retention and account deletion behaviour before production launch.

- Category selection must not rely on color alone.

- Dialogs must support keyboard navigation and focus management.
- Status indicators must include text.

### 17.4 Compatibility

- Chrome extension targets Chrome Manifest V3.

### 17.5 Maintainability

- Keep tracker lifecycle rules in the backend/domain layer.
- Keep analytics metric definitions consistent across dashboard and exports.

## 18. Error and Empty-State Behaviour

The application must provide understandable messages for:

- Invalid Jira URL.
- Ticket ID cannot be extracted.
- Unsupported Jira URL host or path.
- Category not selected.
- Duplicate tracker.
- Invalid GitHub PR URL.
- Duplicate PR reference.
- Tracker no longer open.
- Tracker not found or not owned by the user.
- Session expired.
- Network/API unavailable.
- Excel generation failed.
- PDF generation failed.
- No trackers in the selected date range.
- No PR references in the selected date range.

Do not silently discard user input after a recoverable error.

## 19. Reporting Definitions and Caveats

The product reports activity recorded inside Ticket & PR Tracker. It does not independently verify Jira or GitHub state.

Therefore:
- “Completed tracker” means the user marked the tracker completed in this application.
- “PR count” means the number of unique PR URLs stored.
- “PR activity” means when the user added PR URLs to the application.
- “Merged PRs” must not be shown because merge state is not checked.
- “Jira ticket title” must not be shown because Jira content is not retrieved.
- “Ticket ID” is the identifier parsed from the Jira URL.
- “Development” and “Support” are user-selected categories, not AI classifications.

These definitions must be used consistently in the dashboard, Excel workbook, PDF report, and any future presentation.

## 22. Open Product Decisions

These decisions should be confirmed before implementation is finalized:

1. **Allowed Jira domains:** Is there one company Jira domain, or should users be able to configure multiple Jira hosts?
2. **Ticket ID fallback:** If a ticket ID cannot be parsed from the URL, should users manually enter it, or should the application reject the URL?
3. **Duplicate tickets:** Should one Jira ticket be allowed to have multiple trackers for the same user? Recommended default: no.
4. **Start date editing:** Should users be allowed to backdate or correct the start date after tracker creation?
5. **PRs after completion:** Recommended default is to allow additional PR references after completion without changing the original completion date.
6. **Reopening:** Should completed trackers remain permanently completed in the MVP, or should reopening be supported?
7. **CR terminology:** Confirm whether “CR reference” means GitHub Pull Request reference in the UI and reports, or whether CR is a separate internal reference type.
8. **PDF generation:** Confirm whether PDF generation should run entirely in the browser or through a server-side-compatible PDF service/library. The choice must be compatible with Cloudflare Workers constraints.
9. **Timezone:** Use the browser's local timezone by default, or allow a user preference to be saved.

## 23. Final Product Definition

Ticket & PR Tracker is a simple, user-driven system for recording Jira work and associated GitHub pull-request references.

The product does not integrate with Jira or GitHub APIs in the MVP. It does not use AI. The user supplies the Jira URL, selects Development or Support, and later supplies the relevant PR URL(s).

The Jira URL remains the source of truth. The ticket ID parsed from that URL is the tracker title. The category is explicitly selected by the user. PR URLs are stored and counted without inspecting PR contents or verifying merge status.

The core workflow is:

**Sign in → Create Tracker → Paste Jira URL → Select Development or Support → Track Work → Select Tracker → Add PR URL(s) → Confirm Completion → View Monthly Analytics → Export Excel/PDF.**

The Chrome extension is a lightweight companion that authenticates with this application and makes the Create Tracker workflow available from a Jira browser tab. All core business logic, persistence, analytics, and reporting remain in the main application.
